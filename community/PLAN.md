# ArchGraph 共建共享社区 — 总体规划

> 文档状态: v1.0 草案 | 日期: 2026-09-02

## 1. 愿景与定位

**一句话：** 让每个 Agent 项目的架构知识成为社区的公共资产，通过「架构子图」的
共建共享，形成一套跨项目可复用的 Agentic Engineering 架构语言。

ArchGraph 的核心主张是：**用一张统一的架构图谱（ArchiMate 3.2 意图图）把
harness 设计与目标产品设计放进同一个模型**，从而对 Agent 有真实控制力。
社区把这套理念延伸到**组织层面**——每个项目贡献自己的架构子图，他人可获取复用。

- **不是** Agent 运行时数据交换中心
- **是** 架构子图（能力子图 / 角色子图 / 治理子图 / 业务子图）的注册与发现中心
- 图谱 = 元数据 + 结构（elements/relationships/views），本体与 schema 遵循
  [ArchGraph 框架](../../archgraph) 的 ARCHGRAPH 图谱规范

## 3. 社区架构

```
                    ┌─────────────────────────────────────┐
                    │   ArchGraph 社区图谱库（graph-wiki）  │
                    │   GitHub 托管 + 远程 MCP 服务          │
                    │   assets/graphs/<项目>/<子图>.json     │
                    └────────▲─────────────────▲──────────┘
                   贡献子图  │                 │  获取子图
          graph_submit      │                 │  graph_list/get
              │             │                 │              │
   ┌──────────┴─────┐  ┌────┴─────┐  ┌───────┴─────┐  ┌─────┴───────┐
   │ 项目A (Agent)  │  │ 项目B     │  │ 项目C       │  │ ...          │
   └────────────────┘  └──────────┘  └─────────────┘  └─────────────┘
```

### 3.1 分层仓库结构（建议）

| 仓库 | 内容 | 角色 |
|---|---|---|
| `archgraph` | 框架核心 + 规范 + 文档 | 社区"宪法" |
| `graph-wiki` | 社区图谱共享库 + MCP 部署 | 社区"图书馆" |
| 各 Agent 项目 | 各自的意图图（私有运行） | 社区"居民"（贡献者） |

### 3.2 共享物：架构子图

一个**子图** = 从某项目完整意图图中裁剪出的、有独立复用价值的一块：

- **能力子图**：某 Agent/角色的核心能力及关联（如 aBot 项目总管能力子图）
- **角色子图**：某 Business Actor 及其职责、协作关系
- **治理子图**：可复用的规则/流程/门禁模式
- **业务子图**：某业务域的元素关系（可与技术选型关联）

## 4. 治理模型

### 4.1 角色

| 角色 | 职责 |
|---|---|
| 维护者（Maintainer） | 审核子图提交、维护规范、管理仓库 |
| 贡献者（Contributor） | 提交/更新自己项目的子图 |
| 使用者（Consumer） | 获取复用子图（只读） |

### 4.2 子图质量门槛（graph_submit 自动强制）

提交时服务自动执行 ARCHGRAPH schema 校验，不通过拒收不入库：

1. 结构完整：name/description/elements/relationships/views 必填
2. ArchiMate 类型合法（64 元素类型 / 11 关系类型）
3. id 唯一
4. 关系端点引用存在（source_id/target_id）
5. view 成员与 parent 引用存在
6. 顶层视图唯一

**人工规范（社区章程约定，非自动）：**
- id 命名：`<project>-<domain>-<subgraph>-<seq>`（如 `abot-overseer-capability-001`）
- 每个子图必须有清晰 `description` 说明复用价值
- 关系用 ArchiMate 语义（Association/Assignment/Realization/Serving 等），
  不用全用 Association 兜底

## 5. 运营与激励

### 5.1 贡献流程（已跑通的范式）

```
项目内 Agent/人在用户指引下
  1. 裁剪自己的意图图 → 形成独立复用价值的子图
  2. graph_validate（服务内提交前自动校验）
  3. graph_submit <id> {graph}   → schema 校验 → 入库 → git commit
  4. sourceRepo/sourceCommit 记录来源，可追溯
```

### 5.2 激励

- **署名与可追溯**：sourceRepo + sourceCommit 记录每个子图来源
- **复用红利**：贡献者获取他人子图时，形成"你贡献的架构模式被你复用"的反馈
- **生态增值**：子图越规范越易被复用，越易被复用的项目越有影响力

### 5.3 运营节奏（建议）

| 阶段 | 目标 | 里程碑 |
|---|---|---|
| P0 启动（1-2 周） | 规范就位、2-3 个示范子图 | 本文档 + 贡献指南落地，aBot 子图入库 |
| P1 招募（1-2 月） | 5+ 项目加入 | 各项目贡献 1+ 子图 |
| P2 生态（3 月+） | 形成跨项目复用案例 | 子图被外部项目实际复用 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 子图质量参差 | schema 自动校验 + 人工命名/语义约定 + 维护者审核 |
| 各项目图 schema 演进不一致 | graph-wiki 的 schema 校验统一收口 |
| 激励不足、贡献少 | 维护者主动贡献示范 + 复用案例宣传 |
| 仓库分叉/同步混乱 | 以 GitHub 主仓为准，多设备 pull/push 对齐 |
